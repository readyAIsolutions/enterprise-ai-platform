===============================================================================
PART 0 — WHAT THE WHOLE THING IS (the one-paragraph idea)
===============================================================================
ENI is a self-validating, modular "AI build operating system." One plain-English
goal goes in, a tested program comes out. It is built from:
  * A single orchestration kernel (platform_kernel.py -> PlatformOS) that boots
    and supervises every capability "module."
  * ~50 independent capability modules (in modules/, NOT covered in this digest
    — that is cluster 2) that auto-register with the kernel.
  * Cross-cutting systems: kernel plumbing, foundation libraries
    (policies, evaluations, prompts), orchestration (workflows, plugins,
    feature flags), integration (API gateway, event hub, service mesh),
    monitoring (metrics, alerts, dashboards, logs), and tenancy (per-customer
    isolation for monetization).
  * A newer "cooperative multi-player build floor" (multiplayer/, :8787/:8788)
    where many machines, each with their own GPUs and API keys, build the SAME
    codebase at the SAME time under one coordination server.

The selling story is "a horizontal cooperative build floor": N people * N
machines each run a light client; a central server splits a goal into tasks,
assigns them to the best machine, merges their work, and shows a live board.

Module/system health: HEALTHY, DEGRADED, UNHEALTHY, STARTING, STOPPING,

--- 2.2 LifecycleState (Enum: line 90) ---
The platform state machine:
  UNINITIALIZED -> INITIALIZING -> DISCOVERING -> CONFIGURING -> STARTING ->
  RUNNING / DEGRADED -> PAUSING / PAUSED / STOPPING -> STOPPED, plus CRASHED
  -> RECOVERING. Each state has a whitelist can_transition_to(target), so
  invalid transitions raise. Example allowed moves: STARTING -> {RUNNING,
  DEGRADED, CRASHED, STOPPING}, RUNNING -> {DEGRADED, PAUSING, STOPPING},
  PAUSED -> {RUNNING, RECOVERING, STOPPING}, CRASHED -> {RECOVERING, STOPPING},
  RECOVERING -> {RUNNING, DEGRADED, CRASHED, STOPPING}. A module-level
  _STATE_INDEX provides a numeric gauge for metrics.

--- 2.3 Event system (lines 184-512) ---
  EventPriority: LOW=0, NORMAL=50, HIGH=100, CRITICAL=200.
  Event: dataclass (event_id UUID4, topic, source, payload, timestamp, priority,
    correlation_id, metadata). Factory Event.create(topic, source, payload,
    priority=..., correlation_id=..., metadata=...).
  Subscription: {id, topic, handler (async or sync callable), subscriber_name,
    priority_filter, once(bool)}.
  EventBus: thread-safe pub/sub. Supports async dispatch via a thread-pool
    executor, priority filtering, dead-letter queue, event history
    (_SEEN_HISTORY_MAX 10000), topic matching with wildcards, get_stats(),
    shutdown() (drains the executor).
  publish(): records the event, finds matching subscriptions via
    _get_matching_subscriptions(topic), applies priority filter, dispatches
    (async to executor if enabled; else synchronously). On handler exception it
    routes to the dead-letter queue. publish_sync() runs inline.

--- 2.4 Module and the @module decorator (lines 514-618) ---
  Module(abc.ABC): the base contract every capability module implements.
    State: _meta_name/_meta_version/_meta_config (set by decorator), _config,
    _status (HealthStatus), _started_at, _module_id (UUID4).
    Mandatory async methods: initialize() (bring up), health_check() -> returns
    HealthStatus, shutdown() (teardown). Name/version/status/module_id are
    properties.
  module(...) decorator: registers the class into the global _MODULE_REGISTRY
    dict {name: class}. Usage: @module(name="safety_governance", version="1.0.0").
    Any class so decorated is picked up by ModuleRegistry.discover() with zero
    kernel edits.

      and reads global health poll interval from health.global_interval_sec.
    start():
      must be in CONFIGURING|STOPPED; transitions STARTING; sets started_at;
      awaits module_registry.initialize_all(); determines initial state: if any
      "required" module isn't HEALTHY -> DEGRADED, else RUNNING; records gauges
      (platform.state, platform.modules.initialized, platform.modules.healthy)
      and increments platform.lifecycle.starts; starts background health poll
      loop task; publishes platform.started event.
    shutdown():
      transitions STOPPING, cancels the health poll task, publishes
      platform.stopping, shuts down modules, then STOPPED.
    pause() / resume(): README-advertized features.
      pause() from RUNNING/DEGRADED/RECOVERING -> PAUSING -> PAUSED (stops the
        poll loop).
      resume() from PAUSED -> RECOVERING: re-initializes modules that are
        UNHEALTHY/UNKNOWN (await instance.initialize(); set HEALTHY), restarts
        the health poll, then -> RUNNING.
      _health_poll_loop(): while RUNNING/DEGRADED/RECOVERING, sleep the
        interval, run_all_checks(), _evaluate_platform_health().
      _evaluate_platform_health(reports): if the aggregate "platform" report is
        UNHEALTHY and not already DEGRADED -> DEGRADED; if HEALTHY and DEGRADED
        -> RECOVERING then RUNNING.
      _transition_to(target): validates with the state machine, records to
        state_history, publishes platform.state_change event.
    Accessors: event_bus, module_registry, health_checker, metrics, logging,
      config, platform_id, uptime_seconds, status_report().
    status_report(): high-level status dict {platform_id, state, uptime,
      config{environment, version}, modules{discovered, deque}, events stats,
      metrics snapshot, state_history[last 20]}.
    register_signal_handlers(): installs SIGINT/SIGTERM handlers that schedule
      a clean shutdown() on the running loop.
  create_platform(config_path, modules_path): convenience = instance() + initialize().

Important note: platform_kernel.py is the REAL produced core; the docs in
docs/TECHNICAL_REFERENCE.md describe it (with slightly different class order)
and both agree on behavior.

PART 10 — HOW IT ALL CONNECTS (the wiring summary)
===============================================================================
1. Boot: PlatformOS.initialize() loads config.yaml, builds LoggingBridge,
   EventBus, MetricsCollector, discovers modules (Placeholder registry .discover()
   imports every module/<name>/__init__.py so @module decorators register),
   builds HealthChecker. start() then initializes all enabled modules in
   priority order with startup timeouts, decides RUNNING vs DEGRADED from
   required-module health, records metrics, starts the health poll loop, and
   publishes platform.started.
2. Module contract: every capability (safety_governance, model_router, ...)
   is a class extending Module, decorated @module(...), implementing async
   initialize/health_check/shutdown. The registry bores them; the health
   checker pings them; the event bus connects them via topics like
   safety.incident or platform.started.
3. State machine: LifecycleState tracks the platform; pause/stopped/recovering
   are implemented and resume() repairs unhealthy modules.
4. Events: EventBus.publish(topic, payload). Wildcards and priority filter
   route to subscribers; dead-letter captures failures. The event_hub layer
   provides standardized schemas + contracts on top.
5. API + dashboard: the gateway (:8421) exposes /api/v1/health, /modules,
   /flagg events, /orchestration, /tenants, etc. Same port as the dashboard.
6. Quality & audit: kernel/quality_gate.py explains 17 deployment gates
   (security tests, rollback, data quality, encryption, recovery); kernel/audit.py
   is the tamper-evident SQLite chain; kernel/orchestrator.py coordinates
   specialist agents with evidence-based conflict resolution.
7. Policies / brains: foundation gives policy rules for enforcement,
   evaluation scorecards for model quality, and a prompt registry for
   production prompts (semver, A/B).
8. Multi-tenant: tenancy/tenant_manager.py isolates each customer behind its
   quotas, roles, config, and partitions; the gateway routes by tenant.
9. Telemetry: monitoring/* collects Prometheus metrics (:9090), thresholds
   -> alerts (alert.* events), health snapshots for the dashboard, and
   structured logs.
10. Cooperative build (the new centerpiece): the multiplayer server (:8787/
    :8788) brokers tasks to client machines (:any), each with its own keys;
    planner + vault in local_controller (:8913) turns one prompt into code;
    merges are conflict-safe and integrated only when tests pass.
