## When to use
- Artist wants tracks downloadable behind a gate (like / repost / comment on SoundCloud).
- Artist wants a paid beatpack/sample-pack store.
- Artist wants an admin panel reachable ONLY by their own SoundCloud account.
- User demands "real site, no fake data" (they will reject seeded/demo/payment placeholders).

## Architecture (known-good)
- **Starlette** app in `server.py`, single **SQLite** layer in `db.py` (all tables + idempotent `_migrate()` that `ALTER TABLE` adds columns), **Jinja2** templates in `templates/`, one `static/app.js` + `static/style.css`.
- Fan identity: `fans` table keyed by SC `sc_user_id`, persisted via a `acpeso_fan` remember-me cookie. A fan's purchases live in `fan_purchases(fan_id, beatpack_id)`; favorites in `fan_items`; comments in `fan_comments`.
- Admin is NOT a password. Admin = ONLY when the signed-in SC account matches the artist's account. Grant an admin session cookie in the callback when `_is_admin_fan(fan)` is true. Do not ship a password fallback.
- **Match admin on the SC `sc_user_id`, NOT the username.** SoundCloud's `me()` returns the account's **display name** as `username` (e.g. `"AC PE$0"`), NOT the permalink (`acpeso`). If `_is_admin_fan` compares `username == "acpeso"`, the real owner logs in as a plain fan and it LOOKS like "login is broken / not admin" — the classic "login does nothing" symptom. Fix: store `admin_sc_user_id` = the owner's numeric SC id (grab it from the first login's `fans.sc_user_id`) and match on that first (username/email as fallbacks). Also add an `_AutoAdminSession` middleware so a fan who logged in before the fix is auto-promoted to admin on their next page load (no re-login).

## SoundCloud OAuth + gating
- PKCE: store the verifier between `/connect` and `/callback` (`_VERIFIERS[state]`), generate `state = f"{mode}|{slug}|{sid}"`.
- Gate unlock must **verify against the SC API** (does the fan actually like/repost/comment), never trust a client click. `verify_step()` hits `/me/favorites`, `/me/track_reposts`, `/me/comments`. "Any comment counts."
- **PITFALL — SC returns plain JSON lists, not `{collection:[...]}` wrapper, for `GET /me/favorites`, `/me/track_reposts`, and `/tracks/{id}/comments`.** If `user_liked`/`user_reposted`/`user_commented` call `data.get("error")` on that raw list, Python raises `AttributeError: 'list' object has no attribute 'get'`, which is swallowed by `verify_step`'s `try/except` → every step returns False → the gate says "not verified" even when the fan definitely liked/commented. **Fix: guard with `if isinstance(data, dict) and data.get("error"):` before touching the payload, and rely on `_track_collection()` (which already handles both dict+`collection` and bare list) for iteration.** `_api_get` returns exactly what SC returns, so the type varies by endpoint.
- **A fan with an expired/revoked SC access token gets a silent 401** from every verify → False forever ("gate doesn't work" for that one account). Check by calling the verify helper with each fan's token and inspecting `/me` (returns `{"status":401}` on a dead token). `db.update_fan_token` + per-fan `sc_refresh_token` exist; a robust fix auto-refreshes on 401, otherwise the fan must re-login. The crash bug above masks this because it makes ALL fans fail identically — fix the list/`.get` guard first, then re-test per-fan to surface real 401s.
- **Prefer "open external window + verify-only" over auto-performing the action.** LO explicitly wanted the gate to OPEN the track on SoundCloud in a new tab/window (`window.open(track_url, '_blank')`) so the fan does the like/repost/comment ON SoundCloud, then a separate "Verify" button. So `/unlock/{sid}/{step}` should be **VERIFY-ONLY in live mode** (just query SC and confirm), NOT `like_track()`/`repost_track()`/`add_comment()` on the fan's behalf. Keep the auto-perform branch only inside `if sc.is_mock():` so the unit test that completes steps via `/unlock` still passes (mock records the action as if the fan did it). Return a clear msg when SC doesn't show the step ("Open the track in SoundCloud, do it there, then hit Verify again"). Put `data-track` on the gate element so JS can open it.
- SC api-v2 `/resolve` and `/users/{id}/tracks` return **403 with client_id alone** (OAuth-scoped). Do NOT hardcode "SC API doesn't work" — use the public-profile scrape below instead.

## The key technique: sync the public SC profile without OAuth
>[!NOTE] This public-scrape approach works but ONLY sees the **first page** of the
profile (~10–20 tracks). For a large catalog ("this isn't nearly all my free
beats"), use the **authenticated full-catalog sync** below instead.

To continuously auto-add the artist's "[FREE FOR PROFIT]" tracks to the site (works even when the artist isn't logged in):
1. `GET https://soundcloud.com/{user}/tracks` (HTML 200, ~110KB). Regex `href="/({user}/[a-z0-9-]+)"` to collect permalinks; drop nav links (`/likes`, `/sets`, `/tracks`, `/comments`, `/albums`, `/reposts`).
2. For each permalink: `GET https://soundcloud.com/oembed?format=json&iframe=true&url=<permalink>` → `title` + `thumbnail_url` (t500x500 artwork). Filter `"free for profit" in title.lower()`.
3. For FFP tracks only: `GET https://soundcloud.com/{user}/{slug}`, regex `"id":(\d{6,})`, pick the non-user ID → numeric `soundcloud_track_id` (required for the gate to work). The user id is the `acpeso`-profile user id (e.g. 699988658); skip it.
4. Match existing releases by `soundcloud_url`/track id to UPDATE (never duplicate, preserve uploaded lossless files); else INSERT.
5. Run as a **cron watchdog** (`no_agent=True`, script returns empty stdout when nothing changed, one-line summary when a track is added). Wrapper lives in `~/.hermes/scripts/` because the cron tool requires scripts there; a thin wrapper execs the site-local scanner (so it can `import db`).

## FULL-catalog sync via the authenticated API (large accounts)
When the public scrape undercounts (the artist has many tracks hidden past page 1), pull the ENTIRE catalog with the artist's own OAuth token: after the artist logs in, their access token is stored in `fans.sc_access_token` (many hundred chars, JWT — NOT the old short lived token). Then:
- `GET https://api.soundcloud.com/me/tracks?limit=200&offset=N` with `Authorization: OAuth <token>` (paged; `me().track_count` gives the real total — e.g. one account showed `track_count: 57` but `/me/tracks` returned 91 items, so always paginate to exhaustion via `offset`).
- Filter the `title` for any **free bracket marker**: `[FREE FOR PROFIT]`, `[FREE DL]`, `[FREE DOWNLOAD]`, `[FREE]`, `*Free DL*`, `freedl`, `[FFP]`, `free 4 profit`, `[FR33]`. Match case-insensitively.
- Upsert each as `free_for_profit=1, gate_enabled=1, gate_requires=["like","comment"], featured=1`, matching existing by `soundcloud_track_id`/`permalink_url`, preserving any uploaded `lossless_file`. **LO explicitly dropped repost from the gate (2026-08-02): free-for-profit = like + comment ONLY, no repost.** The DB default column and any code that writes `["like","repost","comment"]` for FFP tracks is WRONG for this user — when syncing/upserting FFP tracks, write `["like","comment"]` so repost never comes back on new uploads. (Paid/featured non-FFP releases can keep whatever the artist sets, but FFP runs like+comment.)
- The stored access token may expire → keep the fan's `sc_refresh_token` and POST `grant_type=refresh_token` to `https://secure.soundcloud.com/oauth/token` to renew (add `db.update_fan_token` helper).
- **\"Sync [FREE FOR PROFIT] says not logged in / returns zero\" — TWO bugs:** (1) `api_sync_ffp` originally matched the admin fan by `sc_username == admin_sc_username`, but SoundCloud's stored username is the **display name** (`\"AC PE$0\"`) not the permalink (`acpeso`), and the fan email is usually blank — so the lookup never finds the row. Fix: also match on `admin_sc_user_id` (the stable numeric SC id). (2) Even when found, the stored `sc_access_token` can be **401-dead on every endpoint** (`/me`, `/me/tracks` all return HTTP 401) while `user_tracks()` swallows that and just returns `[]` → the sync reports `scanned:0` (looks like \"you're not logged in\"). **Diagnose with the raw endpoint:** `curl`/urllib `GET https://api.soundcloud.com/me` with `Authorization: OAuth <token>` — a 401 means the token itself is expired, not a code bug. **A valid refresh is NOT guaranteed:** the stored `sc_refresh_token` may be a junk stub (e.g. 32 chars) that SoundCloud rejects with `invalid_client` on both public and confidential refresh grants — test before trusting it. Robust fix: add `soundcloud.token_valid(token)` (probe `/me`) and `refresh_access_token(...)`; in the sync, if `token_valid` fails try refresh, persist the new token via `db.update_fan_token`, and if still dead return a clear actionable error (\"SoundCloud login expired — reconnect: Log in → SoundCloud as the acpeso account, then sync again\") instead of silently reporting zero. The only real cure for a truly-dead token is a fresh browser consent (`/connect?mode=login` mints a new one in `fans`).
- **Never sync private tracks.** A SoundCloud PRIVATE track has a secret share URL (`https://soundcloud.com/{user}/{slug}/s-<token>`) and/or `public != True` in the API payload. Private tracks break the public SoundCloud widget ("You have not provided a valid SoundCloud URL") and must not appear on a public site. In the sync: filter `public is True` (or `/s-` absent when the field is missing), store the CLEAN direct song URL (strip any `?utm_...` query AND any `/s-…` suffix), and auto-remove any lingering release whose `soundcloud_url` still contains `/s-`. This also fixes the gate's "Open SoundCloud" target to be a direct link to the song, which LO explicitly required.
- **New auto-synced releases must default to NOT featured, and re-sync must preserve the artist's manual choice.** All three FFP sync paths (server.py `api_sync_ffp`, `sync_ffp_api.py`, `scan_ffp.py`) originally hard-coded `"featured": 1` in the payload — so every synced track came in Featured and the artist had to un-feature each. Fix: default the payload to `featured: 0`, and in the `if prev:` (existing-release) branch add `payload["featured"] = 1 if prev.get("featured") else 0` so the artist's manual Featured tick survives the next cron sync instead of being reset. (The manual admin form already defaults new releases to unchecked; `db.upsert_release` defaults to 0. So the ONLY thing forcing feature-on was the sync payloads.) Verify count unchanged after restart: `SELECT COUNT(*) FROM releases WHERE featured=1`.
- Auto-sync cron: make the script print NOTHING when nothing changed (a `no_agent` cron delivers non-empty stdout, so unconditional prints = spam every tick). Only stdout when a new track is added.

## Real Stripe checkout (NO fake paid orders)
User demand: never mark an order paid unless Stripe confirms. Pattern:
- Paid pack → `stripe.checkout.Session.create(mode="payment", ..., success_url=..., cancel_url=...)`, store `session_id` on the order (status `pending`), return `checkout_url`.
- On success redirect AND on `/stripe/webhook` (`checkout.session.completed`, verify `Webhook.construct_event` with `whsec_...`), retrieve the session and flip to `paid` only if `payment_status == "paid"`; record `fan_purchases`.
- Free (price 0) packs bypass Stripe and download directly — genuinely free, not a fake payment.
- If Stripe isn't configured, checkout must REFUSE (400), not fake a sale. Test this.
- **Live keys must be isolated from the throwaway test DB.** `config.apply()` (config.py) already skips `SC_CLIENT_ID`/`SC_CLIENT_SECRET` when `ACPE_DB` is set or mock is forced. You MUST add `STRIPE_SECRET_KEY`, `STRIPE_PUBLISHABLE_KEY`, `STRIPE_WEBHOOK_SECRET` to that same exclusion list — otherwise the live `.env` Stripe secret bleeds into the test DB, `stripepay.enabled()` flips True, and `test_no_fake_stripe_orders_when_not_configured` fails (checkout returns 200 instead of the expected 400). Also, once live keys exist, that test's premise ("not configured") is legitimately false — make it branch on `stripepay.enabled()`.
- **Validate Stripe key prefixes up front:** API **secret** keys start `sk_live_` / `sk_test_`; `mk_...` is a restricted-key / merchant-key that returns a **401 "Invalid API Key"** on `stripe.Account.retrieve()` — don't burn time chasing endpoint bugs, just ask for the `sk_live_...`/`sk_test_...` key. Publishable keys start `pk_live_`/`pk_test_`, webhook secrets `whsec_...`. Distinguish by prefix before debugging anything else. Verify a secret with `stripe_account = stripe.Account.retrieve()` after `stripepay.configure(db)` (Stripe objects use attribute access — `account.id`, not `account.get("id")`). A new account may show `charges_enabled=True` but `payouts_enabled=False` (needs bank details) — charges still work, so a store is live-ready even before payout setup.

## Starlette & test gotchas
- A `Starlette` exception handler for 404 that returns `HTMLResponse(html)` defaults to **HTTP 200** — you must pass `status_code=404` or unmatched routes "succeed". (The `/api/seed` fake-seeder removal was verified via 404.)
- `TestClient` **follows redirects by default** → to assert a 302/303 redirect you must pass `follow_redirects=False`; auth-granting routes may return 307 (Starlette's default `RedirectResponse` status).
- Mock-mode connect auto-creates the admin fan (`mode=login|admin` → username `acpeso` → admin granted). Use it in tests instead of a password login.
- Removing a fake-seeder (`/api/seed`, `seed_curators.py`) breaks tests that POSTed it — rewrite test fixtures to `db.upsert_release(...)` directly into the throwaway `ACPE_DB`.
- **Module-level name shadowing kills every route.** When editing the startup banner / module-level code, do NOT rebind a module-level function name to a local value of the same name — e.g. `_site = _site()` (or `_db = _db()`) at top level makes the FUNCTION name a dict module-wide, so every later `_site()` call raises `TypeError: 'dict' object is not callable` → all tests/routes fail at once. Use a differently-named local (`_s = _site()`) and re-run `pytest` before restarting.

- **Admin flash-message gotcha: query params AFTER a `#fragment` are silently lost.** Redirect patterns like `/admin?tab=curators#curators&msg=...` put `msg` in the URL fragment — the browser never sends anything after `#` to the server, so the flash never displays and a button that worked (e.g. the curator scan) "does nothing" visually. ALWAYS build flash redirects as `/admin?tab=curators&msg=...#curators` (query BEFORE the hash). Also don't double-wrap `urlencode({'m': msg})` — use `urlencode({'msg': msg})`. And the handler that renders the page (e.g. `admin_main`) must read `request.query_params.get("msg")`/`"error"` into the template context, or the template's `{% if msg %}` is always false. When a "button does nothing" with no error, check the flash redirect URL first — it's usually a fragment/encoding bug, not the underlying action failing.
- **Long admin-triggered subprocesses should be DETACHED, not synchronous-with-timeout.** Running `subprocess.run(scan, timeout=120)` on a scan that does dozens of HTTP fetches will hit the timeout and report a false "failed" — and the admin browser waits the whole time. Use `subprocess.Popen([...], stdout=DEVNULL, stderr=DEVNULL, start_new_session=True)` so the request returns instantly and the full job runs in the background; flash "started in the background." (The daily cron does the authoritative recurring run anyway.)
- **Admin Edit form doesn't populate = variable-name mismatch.** The `#newrelease` edit form template reads `release.get(...)` / `release.gate_requires`, but `admin_main` passes the queried record as `edit_release=edit_rel`. When the "Edit" link (`/admin?edit={{ r.id }}#releases`) loads, the form stays blank because it's looking at `release`, not `edit_release`. Fix: in `admin_main` set `release=edit_rel` (or map `edit_release` → `release` in the template), AND make the JS activate the releases/newrelease tab when `?edit=` is present so clicking Edit visibly lands on the populated form. Verify by clicking Edit on a real row and confirming the fields pre-fill (a blank edit form "does nothing" is the tell).
- **"Edit still jumps to the bottom of the page" — replace the page-jump Edit link with an INLINE per-release edit panel.** The old Edit `<a href="/admin?edit={{id}}#releases">` loads the shared form in a `#newrelease` section at the bottom and scrolls there, which LO reads as "goes to the bottom of the page" (a real UX complaint, not a cosmetic one). Fix the same way as the Pitch dropdown: give each release row an `Edit ▾` toggle (`data-edit-toggle`) that flips a hidden `<tr class="edit-row"><td colspan=N>` panel directly under that row, with the FULL edit form pre-filled inline + Save + close ✕. Keep the bottom `#newrelease` form ONLY for "Add new release" — remove the Edit links that point to it. Duplicate the whole form markup per release (it's an admin page, weight is fine). Reuse the same independent-toggle JS pattern as pitch. Verify by POSTing to `/admin/release` with the inline field names (id + all fields, `gate_requires` as repeated `form.getlist`) and confirming a 303 back to `#releases` + the DB row actually changed.
- **`.admin-grid` clips wide content — FIRST check for a CSS class-name mismatch, THEN overflow.** The #1 root cause found on this site (after MULTIPLE failed CSS guesses) was a **class mismatch**: templates mark full-width cards with `class="admin-card admin-wide"` but the CSS rule that spans the grid was written as `.admin-card-wide` (hyphen). The selector never matched, so the full-width rule never applied and cards sat **side-by-side in narrow columns** instead of stacking full-width — the \"right side panel\" that covered the Edit/SC-cover/Delete buttons was literally the New/Edit-release form sitting next to the release table. Symptom LO reports: \"the Edit + 2 other buttons are literally covered / cut off by the right side panel in Releases.\" **Diagnose first with `grep -n 'admin-wide' templates/admin.html` vs `grep -n 'admin-card-wide' static/style.css`** — if the class names differ, THAT is the bug; fix by adding the actual class to the CSS (`grid-column:1/-1`). Then as a secondary safety net for genuinely-wide tables: `table-layout:fixed` + an explicit width for EVERY column (`#releases .admin-table th:nth-child(1){width:34%}` ... `th:nth-child(7){width:auto;white-space:normal}`), `td{word-break:break-word;overflow-wrap:break-word}` so long titles wrap, `td.row-actions{white-space:normal;min-width:150px}` + `.btn-tiny{white-space:nowrap}`, `min-width:0` on grid children, `overflow-x:auto` on the wide card, and `@media (max-width:860px){.admin-wide table{min-width:680px}}` so phones scroll instead of clip. `overflow-x:auto` alone still lets buttons get pushed out — but check the class-name mismatch BEFORE reaching for table-layout, because no amount of column-width CSS fixes a card that was never full-width in the first place.
- Badge classes (`.badge`, `.badge-ok`, `.badge-warn`) are NOT in `static/style.css` by default — add them when introducing status badges in admin tables.
- **LO's "unneeded and outdated" → remove the whole feature, not just the button.** When he flags an admin action as dead weight (e.g. the "SC cover" one-click artwork button), pull it out end-to-end: delete the `<a>`/button from the row, delete the server Route registration, delete the handler function, and confirm the route 404s with no refs left in templates/static/tests. Per his explicit preference (see the Gmail/SMTP removal above), dead UI should be DELETED, not relabeled or hidden.
- **When CSS fixes don't take and LO keeps saying "still cut off" — MEASURE the real rendered layout with a headless browser instead of guessing at CSS.** Repeating overflow-x/table-layout/width guesses is a trap: the bug may be a class-name mismatch or a grid quirk you can't see by reading CSS. Install a real browser and measure the actual bounding boxes: (1) `python3 -m venv /tmp/shotvenv && /tmp/shotvenv/bin/pip install playwright starlette jinja2 httpx` then `/tmp/shotvenv/bin/python -m playwright install chromium`; (2) get an admin cookie (`db.create_admin_session(fan['id'])`), set FAN_COOKIE + ADMIN_COOKIE in a Playwright context, load `/admin?tab=releases`; (3) `page.evaluate` to read `getBoundingClientRect()` of the card vs the last action button and `getComputedStyle(...).gridTemplateColumns`. Seeing `gridTemplateColumns: '559px 559px 0px'` (two columns) or a button whose `right > card.right` instantly proves whether it's a card-width problem or a table-overflow problem — which tells you which CSS fix to apply. (Note: the venv's getsitepackages() differs from the system interpreter's; inject the venv's site-packages into PYTHONPATH when the project deps live in the system python.) This is a general technique: when a layout bug survives multiple CSS edits, stop guessing and measure it.
- **Editable front-page/hero text (the pattern).** LO wanted to edit the homepage copy ("kicker", sub-line, decorative description, newsletter heading/sub) from the admin panel without touching templates. To add an admin-editable string you must touch FOUR places or it silently won't persist/render: (1) add the key to `_site()`'s tuple so it's in the settings dict passed to templates; (2) add it to the `admin_settings` save loop's tuple so POST `/admin/settings` persists it; (3) add an `<input>` in admin.html posting the same `name=`; (4) in the target template render it with a fallback, e.g. `{{ site.get('hero_kicker') if site and site.get('hero_kicker') else 'Independent • 100% free downloads' }}` (blank field → keep current text, since `get_setting` returns `''`). Verify by POSTing test values then GETting the page and asserting the string appears (save returns 303). The existing `tagline` setting is the model to copy.
- **Keep admin section copy in sync with the real backend — and REMOVE dead UI, don't just relabel it.** When the sender migrated from SMTP/App-Password to the Gmail-API OAuth path, the SMTP admin block still taught the dead App-Password flow and said sending was OFF. LO's explicit preference (he said "we don't use this... remove this if we don't need it"): if a mechanism is truly dead, DELETE the whole admin form + inputs for it, not just rewrite its helper text. He wants the panel to only show what's actually used. Removed the SMTP host/port/user/password/STARTTLS form entirely and left only the Gmail-API (Google Cloud) section, retitled "the only email sender", with a one-line "(No SMTP / Gmail App Password is needed.)" note. Verify the dead inputs are gone from the rendered HTML (grep the form name= fields) before calling it done.

### "Uploading a lossless beat just infinitely loads / never uploads" — the Cloudflare TUNNEL, not the app
When the artist reports a lossless WAV/FLAC upload spins forever, the app code is usually fine — **the Cloudflare tunnel throttles request bodies to ~140KB/s** (verified live: 2MB=16s, 5MB=32s, 10MB=timeout through the tunnel, while the SAME file to `http://127.0.0.1:8533` returns 303 in 0.6s). A 20–150MB lossless file therefore takes many minutes, and a plain HTML form submit gives zero feedback → looks like an infinite spinner.
- **First, isolate app vs transport** (don't guess the code is broken): `curl -F lossless_file=@big.wav http://127.0.0.1:8533/admin/release-upload` (local, should be <1s for 20MB) vs the same through `https://<domain>/admin/release-upload`. Local fast + public slow/timeout = tunnel throttling, not a code bug.
- **Print-to-tunnel test gotcha (this project's path has a `$`)**: `cd \"/home/hunter/Desktop/ac pe$0\"` expands `$0` to `bash` → `No such file`. Use the `launch_acpeso.py` python `subprocess(cwd=...)` launcher, and the terminal tool blocks a `workdir` containing `$`.
- **Fix 1 — live progress via XHR.** Replace the silent form submit for lossless with an XHR `FormData` POST to `/admin/release-upload` (the dedicated route) exposing `xhr.upload.onprogress` → set `fill.style.width` + `pct %` + a "Uploading M MB / N MB" message. `xhr.timeout = 0` (large files legitimately take minutes). On `load`, parse the JSON `{ok, mb}` and show "Uploaded X MB — download is now live." This converts the frozen spinner into visible, completing progress. Request stays in place (JSON, not a redirect) so the admin doesn't navigate.
- **Fix 2 — stream to disk, never `await up.read()` the whole file.** Change `admin_release`/`admin_release_upload` to loop `await up.read(1024*1024)` chunks into a list then `local.write_bytes(b''.join(...))` — a 100MB+ WAV must not be loaded fully into RAM. Have `/admin/release-upload` return `JSONResponse({ok, saved, name, size, mb})` instead of a 303 redirect so the progress bar can confirm completion in place.
- **Beware creating PHANTOM releases while testing.** Posting to `/admin/release` with empty `id`/`title` (or only test fields) makes `upsert_release` INSERT new blank releases (verified: 5 phantom rows appeared and had to be deleted by id). When testing uploads, either pass a real release `id` or use `/admin/release-upload` (which requires an existing release); clean up: `DELETE FROM releases WHERE title='' AND id NOT IN (the 16 originals)` + delete matching `storage/*.wav`.
- **A stale duplicate cloudflared can sit next to the real one.** Check `pgrep -af cloudflared`: a leftover pre-named-tunnel quick-tunnel (`cloudflared tunnel --url ...`) can run alongside `cloudflared tunnel run acpeso`, both wired to :8533. Kill the `--url` one (keep the named `tunnel run` one). Doesn't cause the throttle by itself (verified throttling persists with one tunnel) but reduces competing origin connections.
- **R2 broken = non-fatal if wrapped.** The R2 put can fail with an SSL handshake error (dead/misconfigured endpoint) — it's wrapped in try/except so it must not block local save + redirect. If LO later wants big files off the slow tunnel, fixing R2 (or presigned direct-to-R2 uploads) is the real speed unlock; otherwise the progress-in-place fix is sufficient.

Full recipe incl. the admin.html `data-up-upload` markup, the XHR handler, the streaming server change, and the phantom-release cleanup: `references/lossless-upload-tunnel-fix.md`.

### PITFALL — sqlite3.Row has NO `.get()` (live 500, tests pass)
`db.conn()` uses `row_factory = sqlite3.Row`, so a bare `c.execute(...).fetchall()` returns **`sqlite3.Row` objects, not dicts**. If a new helper does `r.get("col")` on those rows → `AttributeError: 'sqlite3.Row' object has no attribute 'get'`, which 500s `admin_main` (dashboard loads in `admin_main`) → the whole admin panel 500s. Locking: the **unit test passed** because the test's own DB was seeded with `db.upsert_...` which returns dicts through the helper path, and the aggregation test used the helper (which internally... still hit the same rows) — but the LIVE render with full data tripped it. **Rule: in db.py helpers, when you loop raw rows use `r["col"]` (indexing), NOT `r.get()`; reserve `.get()` for `dict(r)` or helper-returned dicts.** `releases_missing_lossless()` iterated raw rows with `r.get("title")` → the exact live-500. Tests passing is not proof the live path is clean — hit the REAL `/admin` with a real admin cookie and a populated DB before declaring done.

### PITFALL — a server started BEFORE a code fix still runs the OLD code
After patching `db.py`/`server.py`, the running uvicorn holds the previous in-memory code. If you re-verify against the live server you'll reproduce the ORIGINAL failure (e.g. still 500 on the `.get` bug) and wrongly conclude the fix didn't work. **Restart the server (kill + relaunch, not a reload-less in-place edit) after every code change before live-verifying.** Combined with the project's `$`-in-path quirk, restart via the Python `launch_acpeso.py` launcher / a background terminal session, give it ~2-5s, then confirm the port listening before curling.

- **PITFALL — `\$` is NOT an escape in a normal Python string.** When interpolating the artist name into double-quoted Python strings (`"AC PE\$0 · Daily briefing — {day}"`), `\$` is an invalid escape: Python leaves the literal backslash in AND emits a `SyntaxWarning: invalid escape sequence`. So the subject/brand shows a literal `\` (e.g. `AC PE\$0`) and logs are noisy. Just write `$` plainly (`"AC PE$0"`) — `$` is only special to bash, never to Python string literals. This bit the briefing subject + CLI description; `sed -i 's/\\\$/\$/g'` fixed it. (The `$`-in-path shell expansion problem is a separate, bash-side issue — see the Deploy quirk above.)
