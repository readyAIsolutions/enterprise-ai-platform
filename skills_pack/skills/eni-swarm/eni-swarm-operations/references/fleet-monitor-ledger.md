# Fleet Monitor — running & interpreting `monitor_fleet.py`

Runs as a scheduled cron (`Commander/eni_swarm/monitor_fleet.py`). Its job is to
**report** fleet state by writing `HEARTBEAT_LEDGER.md`, NOT to act on builders.
When this cron fires, run the script, inspect the ledger, cross-check freshness,
report status — do not dispatch or edit builder STATUS files.

## Efficient run pattern (execute_code, absolute paths)
Best invoked through `execute_code` so the whole pass happens in one script:
1. `terminal(f"cd /home/hunter/Commander/eni_swarm && python3 monitor_fleet.py")`,
2. `read_file("/home/hunter/Commander/eni_swarm/HEARTBEAT_LEDGER.md")` to print rows,
3. `stat -c '%y %n' builds/STATUS_BUILDER_*.md` for the mtime cross-check.
4. Optional cross‑reference: read `MASTER_STATUS.md` summary header (lines 1‑30) to confirm
   fleet‑wide DONE/IN‑PROGRESS/BLOCKED counts match the ledger — catches drift between
   the legacy builder floor and the active status hub.

### PITFALL — do NOT parse the ledger inside execute_code
`read_file()` **inside** `execute_code` returns ENI-COMPRESSED content on this
box (the compression wrapper wraps the result), so regexing rows like
`re.match(r"\[([A-Z-]+)\]", line)` silently yields zero matches → empty state
counts with no error. Read the ledger with the standalone `read_file` tool
(uncompressed) instead and compute counts/lists from that, or grep the raw file
via `terminal`. Symptom to watch for: state-count dict comes back `{}` even
though the ledger clearly has rows — that's compression, not an empty file.

NOTE — the runnable `scripts/fleet_monitor_pass.py` (the concise 'compute-don't-dump'
report pass) is on disk under the **`eni-swarm`** category dir, NOT `devops`. Its
absolute path is:
`/home/hunter/.hermes/skills/eni-swarm/eni-swarm-operations/scripts/fleet_monitor_pass.py`
(run as `python3 <that path> /home/hunter/Commander/eni_swarm`). `skill_view` shows the
script exists but not which category directory it lives in, so don't guess a
`devops/eni-swarm-operations/` path — verify with `find / -iname fleet_monitor_pass.py`.

## Zero-padded filenames (key pitfall)
Ledger entries render as `BUILDER_5`, `BUILDER_17`, etc., but on disk the files are
**zero-padded** to two digits: `STATUS_BUILDER_05.md`, `STATUS_BUILDER_17.md`. When
reading a specific builder's STATUS file, ALWAYS zero-pad the number — `read_file`
or `cat builds/STATUS_BUILDER_5.md` fails with `No such file or directory` while the
file is present as `STATUS_BUILDER_05.md`. `glob('STATUS_BUILDER_*.md')` handles this
automatically (regex `STATUS_BUILDER_(\d+)\.md` → int), so listing via glob is safe;
only direct per-builder targeting needs the pad. Use a `lambda n: n.zfill(2)` helper
when iterating a specific subset.

## Cross-check fleet health via MASTER_STATUS.md (not just the builder ledger)
`MASTER_STATUS.md` (auto-generated by `status_hub.py`/worker w2) is the consolidated
hub across the whole `STATUS_ENI*.md` fleet + project STATUS files. To gauge fleet-wide
health, parse it (ideally in `execute_code` with compact aggregates to dodge the
ENI-COMPRESSION wrapper on large outputs):
- Top `## Summary` line gives `ALERTS:` count.
- `## ALERTS (consolidated)` lists numbered `[STALLED IN-PROGRESS]` / `[BLOCKED]`
  entries; count them with `re.match(r"\s*(\d+)\.\s*\[([^\]]+)\]", line)`.
- Main table rows `| <name>.md | <path> | STATE | <last-update> | <age-min> | <alert> |`
  give the aggregate DONE / IN-PROGRESS / BLOCKED tally.

## "Parked, not failing" interpretation (mirror this in reports)
When the ledger/matrix shows all IN-PROGRESS minis STALLED (age > 10 min) AND their
mtimes are old (days–weeks), the fleet is **parked awaiting LO directives**, not
crashed. Symptom signature: hundreds of `[STALLED IN-PROGRESS]` at ages of tens of
thousands of minutes, few-to-zero STATUS files updated today, and the only fresh
touch being an IDLE builder. Report "fleet is parked — no dispatch — no errors",
and recommend (a) LO dispatch directives via `/tmp/eni_ctl_BUILDER_*` FIFOs / master
routing to resume the stalled minis, or (b) marking frozen workspaces DONE to clear
the alert noise. Do NOT present a parked fleet as a failure and do NOT attempt to
repair/restart it — the monitor's job is to report, not act.
⚠️ The sandbox **cwd differs** from the repo — always pass **absolute** paths for the
working dir, and don't `cd` twice across separate `terminal()` helpers if they spawn
independent shells; build absolute paths into each command. Use `read_file` on
`/tmp/ctl_status.json` for the controller health check rather than `cat`.

## How the ledger is produced (parser semantics)
- Scans `Commander/eni_swarm/builds/STATUS_BUILDER_*.md` (cwd as fallback).
- State mapped from STATUS marker: `IN-PROGRESS`/`IN_PROGRESS` -> IN-PROGRESS,
  anything else (incl. `IDLE`, `READY`, `ACTIVE`, `DONE`) -> **DONE**. There is
  no true IDLE output state — idle builders show up as `[DONE]`.
- `[BLOCKED]` in the STATUS file, or the builder number listed in
  `HEARTBEAT_ALERTS.md` (`- BUILDER_<n>` line), forces `[BLOCKED]`.
- Empty/blank STATUS files are skipped (crash guard), so a builder with an empty
  file is simply absent from the ledger — check for gaps (e.g. a missing number).
- `verified=` / `blocker=` / `next=` parsed from `key=value` lines; default
  `unknown` when absent (most builders show `verified=unknown` = normal).

## ⚠️ THE critical heuristic: ledger state ≠ live state
The ledger reflects **on-disk STATUS files, not running processes**. A stale
`[IN-PROGRESS]`/`[BLOCKED]` marker means the builder **froze**, not that it is
working. Always cross-check mtime before calling anything "active":
```
stat STATUS_BUILDER_<n>.md   # compare against current date
```
Observed 2026-08-07: ledger showed 8 IN-PROGRESS + 1 BLOCKED, but every STATUS
file was **13 days stale** (all dated 07-25) -> fleet was dormant/idle, NOT
building. The IN-PROGRESS/BLOCKED entries were frozen artifacts. Only BUILDER_37
had a fresh (same-day) `[IDLE]` mtime. Verdict: fleet idle, nothing routing.

## Controller health check (confirm "nothing in flight")
- `curl -s --max-time 5 http://localhost:8940/status -o /tmp/ctl_status.json`
  then inspect the file (do NOT pipe curl into python3/jq — security scanner
  flags `curl | python3` as command injection and stalls the call).
- ⚠️ Pitfall: if the first `curl` in a pass times out / writes an empty file, a
  later successful `curl` rewrites /tmp/ctl_status.json with real bytes — but
  `read_file` on that path may still return "unchanged"/stale content from the
  earlier (empty) read due to its dedup cache. If `read_file` refuses to show
  fresh controller output, fall back to `cat /tmp/ctl_status.json` via
  `terminal`. Verify the size (`wc -c`) before trusting it — an empty file means
  the controller endpoint didn't answer that attempt (retry, don't conclude
  "controller down" from one empty file).
- `HEARTBEAT_ALERTS.md` may be entirely ABSENT — that's normal = no alerts, no
  forced `[BLOCKED]`. Only treat a ledger `[BLOCKED]` as real if the STATUS
  file itself carries the marker or is freshly mtime'd; otherwise it's a stale
  artifact like `[IN-PROGRESS]`.
- Watch: `"queue": {"pending": 0}` (nothing waiting to route), `"free_router":
  "healthy"`, cooldowns `{}`, model list populated.

## Fast liveness probe (complements the mtime + queue checks)
The mtime cross-check proves STATUS files are stale, and `queue.pending=0` proves
nothing is queued — but both are bookkeeping. For a hard "is anything actually
running" answer, run two cheap probes in the same pass:
1. **Count live control FIFOs**: loop `os.path.exists(f"/tmp/eni_ctl_BUILDER_{n:02d}")`
   for 1..N. A healthy active fleet has a FIFO per builder; a dormant one has
   ~0–1 (observed 2026-08-07: only 1 of 50 existed, BUILDER_50 from hours earlier).
   Also note `ls -la /tmp/eni_ctl_DEMIURGE3D_B*` — a *different* fleet's FIFOs may
   be present and should not be mistaken for the ENI swarm's.
2. **Scan for worker processes**: `ps aux | grep -iE 'hermes|mini|builder|swarm\.BUILDER'`
   minus grep. If only the proxy / free_router / controller / gateway are up and no
   builder worker (PTY/bridge) is listed, the fleet is idle.
Combine: `mtime stale` + `queue.pending=0` + `~0 live FIFOs` + `no worker procs`
=> definitive "dormant, nothing in flight" without ever trusting the ledger state
markers. (This is exactly the ledger≠live cross-check, made independent.)

## Housekeeping pitfall: runaway `find /` diagnostics
Terminated BUILDER idle-check sessions leave behind a straggler
`find / -iname STATUS_BUILDER_<n>*` (parent bash also lingers). It burns ~50% CPU
scanning the whole filesystem indefinitely. If `ps aux | grep "find / -iname"`
shows one, kill both the find PID and its parent bash PID. Cheap, safe cleanup.

## Two diagnostics that surprise on first pass
- **`HEARTBEAT_ALERTS.md` is often ABSENT.** `monitor_fleet.py` reads it (if present) to
  build the `blocked_builders` set; when the file doesn't exist the set is empty, so a
  `[BLOCKED] BUILDER_n` row then means the BLOCKED state came from that builder's OWN
  status file — NOT a forced block from the alerts ledger. Don't assume a BLOCKED row
  implies an alerts-file entry, and don't treat a missing alerts file as an error.
- **Zero-padded filenames vs non-padded ledger names.** Files are `STATUS_BUILDER_05.md`
  but ledger rows say `BUILDER_5`. A `comm -23 <(ls ... | sed 's/STATUS_//;s/\.md//' | sort)
  <(awk '{print $2}' ledger | sort)` cross-check will spuriously list BUILDER_01..09 and
  BUILDER_20 as "missing" purely due to padding/sort mismatch. Normalize (`sed 's/0*//'`
  on the numeric part, or strip to the bare number on both sides) BEFORE diffing, or you'll
  chase a phantom missing-builder that isn't there.

## Confirm a surprising ledger classification by re-running (not just reading)
The ledger row for a single builder is written fresh each run, but its state comes
from whatever the STATUS file last had at that instant. If one builder's ledger state
looks anomalous (e.g. IN-PROGRESS on an otherwise-dormant fleet, or conflicts with the
file's own `[IDLE]`/`[DONE]` comment line), do NOT report it — re-run `monitor_fleet.py`
a couple times (foreground loop) and confirm the classification is stable before writing
the report. A one-off IN-PROGRESS that flips to DONE on re-run = stale-run artifact, not a
live build. Cross-check the file's mtime too: fresh mtime + IDLE/DONE comment = live
heartbeat; old mtime + IN-PROGRESS marker = orphaned marker, not activity.

## Idle-check tie-in
A builder slot that shows `[DONE] ... verified=unknown blocker=unknown next=unknown`
in the ledger corroborates "idle, nothing routed" (see `builder-idle-slot-check.md`).
No roster/dispatch + empty controller queue + missing control FIFO = no-op.

## BLOCKED-without-alerts nuance
The script seeds `blocked_builders` ONLY from `HEARTBEAT_ALERTS.md` (`- BUILDER_N`
lines). When that file is absent (common on a dormant fleet), every `[BLOCKED]`
row in the ledger comes from the builder's own on-disk `STATUS_BUILDER_N.md`
content (the `BLOCKED` keyword), NOT from a live alert. Treat a BLOCKED row as
orphaned/stale just like old-mtime IN-PROGRESS — cross-check its mtime before
reporting it as a real blocker.

## Second truth source: MASTER_STATUS.md cross-check
For a richer report, also read `MASTER_STATUS.md` (auto-generated same-day by
`status_hub.py`, header line gives the run timestamp). It aggregates EVERY
`STATUS_ENI*.md` + live-project `STATUS_*` and lists consolidated alerts with
ages. Read its Summary counts (DONE / IN-PROGRESS / BLOCKED / ALERTS) and its
`## ALERTS (consolidated)` section.

### Carried-over / known-durable BLOCKED entries — do NOT re-alert
MASTER_STATUS shows a small constant set of BLOCKED rows (e.g. `ENI9_W3` on
missing creds, `GATE` on the real-USB black-swan data path / unmounted
`/run/media/hunter/DEMIURGE`, `SB_AVR`). These re-appear every run because their
source STATE files are old (ages in the tens-of-thousands of minutes) and their
blockers are environmental/deferred, not newly failing. When they appear, name
them once as **carried-over / pre-existing and documented**, in a bottom-line
sentence — not as a fresh ALERT. Only flag something as NEW if it is both
recent-mtime AND BLOCKED/non-DONE. An honest report separates "no new failures —
dormant, awaiting LO directives" from the recurring BLOCKED backdrop.

### PITFALL — dual-HEARTBEAT_LEDGER.md risk. `monitor_fleet.py` writes `HEARTBEAT_LEDGER.md` to the **process CWD**, not to `_WORKDIR` (the `builds/` subdirectory where STATUS files live). This means:
- Run from `/home/hunter/Commander/eni_swarm/` → LEDGER lands at `Commander/eni_swarm/HEARTBEAT_LEDGER.md`
- Run from `builds/` subdirectory → LEDGER lands at `builds/HEARTBEAT_LEDGER.md`
- If the cron CWD ever differs, the two LEDGER files can diverge.

**Always check both locations** when comparing current vs prior LEDGER state. The authoritative one is `Commander/eni_swarm/HEARTBEAT_LEDGER.md` when run via the standard cron pattern. If `builds/HEARTBEAT_LEDGER.md` exists and differs, it's from an older or manually-triggered run — reconcile before reporting deltas.

## Post-run: sync the duplicate ledger

After the script runs and writes `HEARTBEAT_LEDGER.md` at cwd, sync the stale copy that may exist in `builds/`:

```bash
cp /home/hunter/Commander/eni_swarm/HEARTBEAT_LEDGER.md \
   /home/hunter/Commander/eni_swarm/builds/HEARTBEAT_LEDGER.md
```

This prevents cross-referencing confusion when another tool or human later reads `builds/HEARTBEAT_LEDGER.md` and sees outdated state. The sync is a mechanical copy — the builds copy should always mirror the authoritative cwd copy.

## Post-run diagnostic: zero-byte builder files

After syncing, check for 0-byte STATUS_BUILDER_*.md files — these indicate the builder's initial write crashed before producing any content:

```bash
find builds/ -name 'STATUS_BUILDER_*.md' -size 0 -print
```

If found (e.g. BUILDER_20 is a known 0-byte artifact), note them in the report as crash artifacts that may need reinitialization. The script skips them silently, so they won't appear in the ledger at all.

## Post-run diagnostic: FIFO provisioning audit

Count how many builders actually have control FIFOs vs the expected 50:

```bash
ls -la /tmp/eni_ctl_BUILDER_* 2>/dev/null | wc -l
```

The result is the `provisioned_fifo_count`. If it's far below 50 (e.g. 1/50 as observed), most builders are not reachable via the FIFO control channel and can only be dispatched through PRODUCT_LEAD or direct Hermes routing. Report the count in the summary.
