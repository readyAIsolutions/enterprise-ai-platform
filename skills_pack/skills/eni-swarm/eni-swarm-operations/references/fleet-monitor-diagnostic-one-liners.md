# Fleet Monitor — known-good no-dump diagnostic one-liners

When the ENI-COMPRESSED / `read_file`-dedupe SNAFU bites (see
`fleet-monitor-concise-summary.md`), these copy-paste commands compute the answer
without dumping large output. All verified working from
`/home/hunter/Commander/eni_swarm`. Run them via `execute_code`/`terminal`, NOT
`read_file` (read_file line-number-prefixes the 1st read and returns
"unchanged" on the 2nd, so you can't recover elided rows).

**Ledger state counts** (one-liner substitute for reading the full ledger):
```bash
awk '{split($1,a,"["); split(a[2],b,"]"); c[b[1]]++} END{for(k in c)print k, c[k]}' HEARTBEAT_LEDGER.md
```

**Pull a specific subset only** (blocked / in-progress rows, keeps output tiny):
```bash
grep BLOCKED     HEARTBEAT_LEDGER.md
grep IN-PROGRESS HEARTBEAT_LEDGER.md
```

**mtime freshness cross-check — the source of truth for dormant-vs-live:**
```bash
stat -c '%y' builds/STATUS_BUILDER_*.md | awk '{print $1}' | sort | uniq -c
```

**Which builder freshly checked in** (spot the single parking-date signature):
```bash
find builds -name 'STATUS_BUILDER_*.md' -newermt '3 days ago' -printf '%f %TY-%Tm-%Td %TH:%TM\n' | sort
```

**Which builder FILE is empty** (crash-guard dropped it from the ledger — expected, NOT a lost worker):
```bash
find builds/STATUS_BUILDER_*.md -size -6c -printf '%f empty\n'
```

**Dormancy confirmation — no live builder/master/monitor process running:**
```bash
ps aux | grep -iE 'eni_builder|monitor_fleet|builder_[0-9]|master_driver' | grep -v grep
```

**IDLE builders misclassified as DONE in the ledger** (the monitor_fleet.py non-bracket IDLE pitfall — see fleet-monitor-ledger-read-pitfalls.md §4):
```bash
head -q -1 builds/STATUS_BUILDER_*.md | grep -in '\bIDLE\b'
```
Any hit means a builder is genuinely parked but the ledger labels it `[DONE]`. Cross-check with FIFO existence: if `/tmp/eni_ctl_BUILDER_N` is absent, the IDLE label is correct and the ledger is wrong.

**Control-FIFO census** — leftover FIFOs don't imply live workers; a builder whose file is
marked IDLE has NO `/tmp/eni_ctl_<name>` FIFO (that lack is itself the confirmation it's parked):
```bash
ls /tmp/eni_ctl_* | sed 's|.*eni_ctl_||' | sort | uniq -c
```

## MASTER_STATUS.md is huge — never full-read it (context flood)
`MASTER_STATUS.md` is ~113KB / ~1056 lines (the status_hub consolidates ~598 minis). A full
`read_file` floods context and often triggers the ENI-COMPRESSED head+tail elision anyway.
Instead, slice it:
- **Alert census without dumping rows:** `search_files` (target=content, output_mode=count,
  pattern=`YES`, path=`MASTER_STATUS.md`) returns an exact count of alerpline rows (e.g. 391).
- **Read only the head table + tail summary:** `read_file` with `limit` (~60) at `offset` ~25
  for the table header, then a second `read_file` near the end if the summary/legend matters.
  The header names the alert rule (BLOCKED OR [non-DONE AND age>10min]); a YES count far
  above the BLOCKED total means most alerts are stale IN-PROGRESS → swarm is mostly parked,
  not failing. That one count is often all you need to conclude dormancy.
- These are generated by status_hub.py every 5 min, so age columns dwarf — treat `age`
  as informational, the state+alert columns as the signal.

## Filename pitfall: zero-padded builder numbers
`ls builds/STATUS_BUILDER_<N>.md` for N<10 FAILS because files are zero-padded as
`monitor_fleet.py`'s regex
`STATUS_BUILDER_(\\d+)\\.md` strips the leading zero, so the ledger prints `BUILDER_5`
while the on-disk file is `STATUS_BUILDER_05.md`. This is NOT limited to `ls` — the same
non-padded reference fails for EVERY lookup tool. Confirmed in the field:
`find builds -name 'STATUS_BUILDER_[45].md'` returns nothing AND
`grep 'STATUS_BUILDER_4\\.' builds/STATUS_BUILDER_*.md` returns nothing, because those
names literally do not exist on disk (`_04.md`/`_05.md` only). Do NOT treat a ledger entry
as a missing file / lost worker just because a non-padded `ls`/`find`/`grep` for
`STATUS_BUILDER_4.md` finds nothing or reports an empty bytestring — glob with a wildcard
(`STATUS_BUILDER_*.md` then match the zero-padded variant) whenever reconciling ledger
entries back to on-disk files, and `stat -c%s` the real file to distinguish a true empty
file (crash-guard) from just-wrong-name. Confirmed: exactly 50 files spanning builders
1–50, all padded to two digits.

## PITFALL — don't `%`-interpolate a `python3 -c "..."` inside execute_code
When you route the mtime/freshness calculation through `execute_code` and build the
command with `terminal(f"... % base" % base)` (or `"...".format(...)`) wrapping a
`python3 -c "<script>"` that ITSELF contains Python format specifiers (`%d`, `%s`,
`.2f`, `\\d+` regex, etc.), the outer `%`-interpolation and the inner script collide:
the outer call tries to substitute the script's own `%`-specifiers and throws
`TypeError: not enough arguments for format string`. It fails at runtime, silently
killing the whole diagnostic pass.
Fix: don't interpolate a script-with-specifiers. Write the Python diagnostic to a
temp file (e.g. `write_file('/tmp/fleet_diag.py', ...)`) and run `terminal("python3
/tmp/fleet_diag.py")`, OR pass `base` as a substitution that does NOT appear inside
the inner script (use an absolute path literal in the script and no `%` formatting on
the outer command). Same collision applies to `str.format` and f-strings wrapping
inner regex/format code — prefer a standalone script file for anything with `%`/`\\d`
in the body.

## Interpretation (the point of running these)
If mtimes all cluster on an old date (even when the ledger shows e.g. 8 IN-PROGRESS + 1
BLOCKED) AND `ps` shows no builder process AND the one fresh-mtime builder's file body says
IDLE / no-task / "do not invent work", the fleet is **dormant** and the pass is report-only.
A single fresh mtime whose body is an IDLE check-in is the parking-date signature, not active
work — do not spin up or dispatch (see `fleet-staleness-interpretation.md`).

## Also probe the ORCHESTRATOR processes to state the root cause
Dormancy has two distinct process signatures; naming which one you found makes the report
actionable for the live session that must resurrect the fleet:
- **Dead MASTER / no driver process** → root cause is no directive source. Confirm via
  `ps aux | grep -iE 'eni_master|master_driver|status_hub'` (empty/missing) and a stale
  `STATUS_MASTER.md` mtime weeks old. Builders park waiting on FIFOs that will never be fed.
## Three-factor "floor-dead" probe (proves fleet down vs. monitoring alive)
A regenerated ledger + a freshly-updated `MASTER_STATUS.md` can still look GREEN while
all ~50 builders have been dead for weeks, because `monitor_fleet.py` and `status_hub.py`
re-parse the same frozen `STATUS_BUILDER_*.md` contents on their cron tick. Do NOT trust
the parsed states — the content is a Jul-25 patch. Run these three together; if all hold,
the floor is down regardless of what the ledger/hub says:
```bash
# 1) Builder-worker process count (expect 0 if builders dead).
#    NOTE: controller/daemon infra (eni_local_chat.py, eni_controller serve,
#    eni_kb_daemon) MATCHES a naive 'eni|builder' grep — those are NOT builders.
#    Filter them out explicitly or you'll get a false "alive".
ps aux | grep -iE "python.*(eni|builder|mini)" | grep -v -iE "local_chat|controller|kb_daemon" | grep -v grep | wc -l
# 2) FIFO control-channel count (expect ~0, not 50):
ls /tmp/eni_ctl_BUILDER_* 2>/dev/null | wc -l
# 3) Newest STATUS_BUILDER mtime (expect weeks old, e.g. 07-25 while today is 08-15):
ls -la --time-style=+%m-%d_%H:%M builds/STATUS_BUILDER_*.md | awk '{print $6, $7}' | sort | tail -1
```
If (1)=0, (2)≈0, and (3) is stale → the builders are down; what's alive is only the
5-min monitoring/status-hub cron. Report dormancy (first report is the deliverable,
then `[SILENT]` on subsequent cycles per fleet-staleness-interpretation.md). Do NOT
dispatch tasks or edit STATUS files from this report-only cron.

- **Turbocharger alive but silent** → heartbeat/runner process up (`--port` in `ps`), but with
  no visible log output and zero child builder processes. This is a cycling watchdog with no
  task load, NOT a working fleet — do not mistake a live orchestrator PID for a live build.
Confirm the discriminator with `ps aux | grep swarm_turbocharger` (uptime) + check its log
dir is empty/absent. This "alive PID but no work under it" distinction is the single most
useful signal for the recovery session deciding WHETHER to restart the floor.

**Second-pass "no-change since last run" check** (for a repeat/report-only cron that NOT
regenerates the ledger each run — answer "anything new?" without re-reading everything):
After `python3 monitor_fleet.py` writes the ledger, diff it against a saved snapshot from the
prior run to prove no state drift. `builds/HEARTBEAT_LEDGER.md` is the previous monitor pass's
snapshot on this box:
```bash
diff /home/hunter/Commander/eni_swarm/HEARTBEAT_LEDGER.md \
     /home/hunter/Commander/eni_swarm/builds/HEARTBEAT_LEDGER.md \
  && echo "NO DIFF — full result unchanged"
```
Exit 0 + "NO DIFF" is an authoritative "nothing new, state frozen" answer (no BLOCKED added,
no state transitions) that lets the cron report `[SILENT]`-style without dumping the whole
ledger. Pair with the liveness one-liner (`ls /tmp/eni_ctl_BUILDER_* | wc -l`, no fresh
`.alive_*`, no builder PIDs) to conclude "fleet parked, not actively processing."
Note: the monitor does NOT re-read STATUS files between runs this way — the diff proves the
ledger output is byte-identical, which combined with no new BLOCKED rows means the fleet state
is genuinely frozen (matches the "dormant-but-consistent" signal in
fleet-staleness-interpretation.md).
