# monitor_fleet.py — parsing truth & how to read fleet state correctly

## Where it lives / what it does
`/home/hunter/Commander/eni_swarm/monitor_fleet.py` runs as a cron job. It globs
`builds/STATUS_BUILDER_*.md`, classifies each into DONE | IN-PROGRESS | BLOCKED,
and writes `HEARTBEAT_LEDGER.md` next to the script. It also reads `HEARTBEAT_ALERTS.md`
(if present) to force-block builders listed there.

## PITFALL — `verified=unknown` is EXPECTED, not a failure
The analyzer only extracts `verified=`, `blocker=`, `next=` for status files that
actually use that **`key=value` format** (e.g. B4, B37). Most builders write freeform
prose / `[STATE]` markers (`# STATUS_BUILDER_XX — IN-PROGRESS —`, `# TASK: ...`), so
those fields come back `unknown`. A ledger full of `verified=unknown blocker=unknown`
does **NOT** mean the fleet is broken — ESCAPE the trap of escalating it.
Only trust `verified=`/`next=` when the source file demonstrably uses `k=v` syntax.

The robust signal to read instead is **file mtime** (filesystem truth):
`ls -lt builds/STATUS_BUILDER_*.md`. A status file older than weeks = that builder has
been parked since then; a just-touched file = live.

## Distinguishing IDLE/PARKED vs FAILING — the actual diagnostic sequence
Before reporting "stall" or "blocked", confirm whether anything is even RUNNING:

1. `ps aux | grep -iE "swarm|orchestr|worker|mini"` — swarm builders are usually
   hermes-chat / mini procs; if none except a watchdog/daemon (`swarm_turbocharger.py
   --port 8922`) are alive, the fleet is IDLE, not stalled.
2. Check `/tmp/eni_ctl_BUILDER_*` FIFOs. `ls -la` shows their last-touch mtime.
   A builder whose FIFO "does not exist" (e.g. B37) is truly parked awaiting an LO
   directive — recreate the FIFO before expecting any work.
3. Read `MASTER_STATUS.md` (auto-regenerated by `status_hub.py` every run). It is the
   authoritative consolidation: "598 minis (207 done / 388 in-progress / 3 blocked),
   391 ALERTS". Its own alert rule: raise on STATE==BLOCKED, or STATE != DONE AND
   age > 10 min.
4. When the vast majority of "IN-PROGRESS" entries are 47k–53k minutes old (~33+ days),
   that is STALE NOISE from a previously parked wave — not a live in-flight build.

## Bottom-line framing for an LO report
If status files are weeks old, no worker procs are running, and the "blocked/alerts"
are all week+-old stale markers → the honest report is **"fleet is PARKED, all workers
awaiting an LO directive"** — NOT "N builds are blocked". Escalate only fresh failures
(recent mtime + real BLOCKED state + a running process that died). To resume any
stream, LO must issue a directive through the per-builder `/tmp/eni_ctl_BUILDER_*`
FIFO (several are missing and need recreating).
