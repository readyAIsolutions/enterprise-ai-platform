# monitor_fleet.py + status_hub.py — two fleet-status truth sources

There are TWO distinct fleet-status surfaces in `/home/hunter/Commander/eni_swarm`. Do not confuse them.

## 1. `monitor_fleet.py` — builder-level ledger (narrow scope)
- Regenerates `HEARTBEAT_LEDGER.md` from `builds/STATUS_BUILDER_*.md` (the 50-worker pool).
- Output line format: `[STATE] BUILDER_N verified=… blocker=… next=…`
- State parsing is forgiving: looks for `[IN-PROGRESS]`, `# STATE: …`, `[... BLOCKED ...]`, then falls back to the first `[TOKEN]` on the first non-blank line; anything not BLOCKED/IN-PROGRESS maps to DONE.
- `HEARTBEAT_ALERTS.md` is the blocked-builder list (`- BUILDER_N`); if present, forces those builders BLOCKED. Empty/nonexistent = no hard blocks.
- Run: `cd /home/hunter/Commander/eni_swarm && python3 monitor_fleet.py`
- Scope is ONLY the builder pool ledger — do NOT quote it as the fleet-wide health number.

## 2. `status_hub.py` → `MASTER_STATUS.md` — authoritative fleet-wide aggregate
- Regenerated by a 5-min self-heal cron (also by worker w2 / ENI12 STATUS HUB mini). Controls `status_hub.cron.log`.
- Snapshot header gives quick health: `DONE / IN-PROGRESS / BLOCKED / ALERTS` counts.
- **Alert rule (explicit in the file):** ALERT raised when `STATE==BLOCKED`, OR (`STATE != DONE` AND `age > 10 min`). Applies per-mini across `STATUS_ENI*.md` + every live-project `STATUS_*` (demiurge_scaffold/ recursive).
- Per-mini table rows: `mini | path | state | last-update | age(min) | alert`. `age` is from the file mtime (filesystem truth).

## Pitfall — fresh hub ≠ alive workers (the big one)
MASTER_STATUS.md / status_hub regenerating on time does NOT mean the worker/ENI STATUS files are live.
- The control plane (eni_controller :8940, swarm_turbocharger :8922, status_hub cron) can be fully healthy and regenerating the hub every 5 min **while** every worker STATUS_BUILDER_*.md / STATUS_ENI*.md is frozen for 15–22 days.
- A large `ALERTS` count (e.g. 391) means mostly *stale IN-PROGRESS* files — thousands of minutes old — **not** hundreds of real-time failures.
- Correct read: check the **worker per-file mtimes** (e.g. via `ls --time-style=full-iso builds/STATUS_BUILDER_*.md` or the `fleet_mtime_staleness.py` probe), not the hub's own freshness. "IN-PROGRESS on a 19-day-old file" = dormant/frozen worker, not actively building.
- Builders left `DONE` with `verified=unknown` should not be trusted as verified; flag for a re-verify pass if a tasking wave is coming.

## Recommended end-to-end monitor recipe
1. `cd /home/hunter/Commander/eni_swarm && python3 monitor_fleet.py` → get builder ledger.
2. `head -25 MASTER_STATUS.md` → fleet-wide DONE/IN-PROGRESS/BLOCKED/ALERTS + alert rule.
3. Cross-check worker liveness via actual STATUS file mtimes (fresh hub alone is NOT proof of live workers).
4. Report: control-plane health + worker staleness separately — they decouple.
