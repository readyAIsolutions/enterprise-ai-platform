# Fleet-health assessment: ledger flags vs the authoritative MASTER view

Applies to: any cron job or human run of `monitor_fleet.py`, and any "what's the
real state of the swarm" question. Reading only the ledger / STATUS files gives a
WRONG picture of liveness.

## The core trap: stale state flags ≠ live work

`monitor_fleet.py` regenerates `HEARTBEAT_LEDGER.md` by keyword-scanning
`STATUS_BUILDER_*.md` files for `IN-PROGRESS` / `BLOCKED` / `[STATE]` tokens. It
does NOT check whether anything is actually running. After a swarm went dormant,
these files keep their old `[IN-PROGRESS]` / `[BLOCKED]` markers forever, so the
ledger reports "5 IN-PROGRESS, 1 BLOCKED" that are all **stale artifacts**, not
live work. Never treat ledger state flags as liveness.

## The correct assessment order

1. **Run the monitor** (`python3 monitor_fleet.py` in `eni_swarm/`) to refresh
   `HEARTBEAT_LEDGER.md`. Note its `[STATE]` flags are only a *starting hint*.
2. **Read `MASTER_STATUS.md`** — auto-generated by `status_hub.py` (a swarm worker
   "status_hub"/"w2"). This is the authoritative consolidation of every
   `STATUS_ENI*.md` + live-project `STATUS_*`. It computes real staleness
   (`age` minutes) and raises `ALERTS (consolidated)` — every `>10m stale`
   `[STALLED IN-PROGRESS]` entry is a task that has NOT advanced. Check its
   `Generated:` timestamp is fresh (minutes old, not days).
3. **Verify live infra, not just files**: `ps aux | grep -iE "eni|builder|swarm"`,
   and `ss -tlnp` for the controller ports (`eni_controller` :8940,
   `swarm_turbocharger` :8922, swarm dashboard :8420). Listening ports + alive
   daemons = infra is up even when no builder is working.
4. **Cross-check per-builder freshness**: `ls -lt builds/STATUS_BUILDER_*.md` —
   a file untouched for weeks (e.g. Jul 25) is dormant regardless of its `[STATE]`
   token. A file updated today with a clear `IDLE ... awaiting directive` + a
   missing control FIFO is the signal that a builder is parked, ready, waiting.

## Diagnostic tell — a parked-but-ready builder

B37 pattern: STATUS updated recently, body says `IDLE`, `blocker=none`,
`next=await LO's directive via /tmp/eni_ctl_BUILDER_37 FIFO creation`, and the
FIFO `[ -e ] NO_ENTRY`. Conclusion: builder alive & ready, just needs LO to create
the control FIFO and write a directive. This is the "ready slot" to report when
LO wants to re-awaken the fleet.

## Distinguishing "monitor healthy" from "fleet healthy"

A self-healing monitor (ledger regenerates, hub re-runs) can report a "healthy"
pulse while the underlying fleet is completely idle. Separating these two claims in
the report is the difference between a useful fleet status and a misleading one:
- Monitor/telemetry layer healthy = script runs clean, hub `Generated:` fresh.
- Fleet healthy = live daemons/ports up AND status files advancing (recent mtime).
- "Fleet idle but nothing broken" = daemons/ports up, but ~400 stale IN-PROGRESS
  tasks untouched for weeks and no active builder processes. That is NOT a failure,
  but it is not "healthy" either — report it as dormant and name the ready slot.
