# Interpreting a parked / idle fleet (the "not broken, just idle" case)

## The trap
When you run `monitor_fleet.py` (or any fleet heartbeat) and the ledger shows several
`[IN-PROGRESS]` and a `[BLOCKED]` builder, it is tempting to raise an alert. **Do not.**
In a parked fleet these entries are almost always STALE — the script just echoes whatever
state token sits in each `STATUS_BUILDER_*.md`, regardless of when it was written.

## status_hub / MASTER_STATUS counts are noise, not the ledger
When reading `MASTER_STATUS.md` (regenerated by status_hub.py), the headline numbers
(`388 IN-PROGRESS`, `391 ALERTS` over ~598 tracked minis) are MOSTLY STALE-DORMANT artifacts:
STATUS_ENI* files whose `last-update` is weeks old (26k-46k min) still count as
IN-PROGRESS+ALERT.

## The dormancy check-in signature (do NOT misread as activity)
A long-idle fleet frequently shows **exactly one** builder file freshly touched while all
others sit weeks old. This is a solo worker's periodic self-check-in: it re-verifies its
control FIFO (e.g. `BY` / `BUILDER` writing "no /tmp/eni_ctl_* for me" and re-stating it is
IDLE/parked) and touches its STATUS file. **A fresh touch whose state token is `IDLE` /
"AWAITING DIRECTIVE" is a check-in confirming "still parked" — it is NOT evidence of
building and NOT a reason to report the fleet as live or partially live.** Only treat a
fresh file as real activity when its token is `[IN-PROGRESS]`/`[BUILDING]` AND a backing
builder process is actually running (see liveness-probe-pitfalls). Rule: read the state
token of the fresh file, don't just count fresh files.

## Ledger line count < on-disk STATUS file count is normal
`monitor_fleet.py` crash-guard-skips empty/0-byte STATUS files, so ledger lines can be
fewer than files on disk (e.g. `STATUS_BUILDER_20.md` is 0 bytes → 50 files, 48 ledger
lines). Expected, not data loss.

## Deliverable semantics: a DORMANT fleet is STILL a report — do NOT [SILENT]
Note: this was formerly phrased as "the correct output is often [SILENT]" — that is
SUPERSEDED. Do NOT suppress the broadcast with `[SILENT]` on a no-change run just because
the verdict repeats last cycle's. The fleet-status pulse IS the deliverable, not a
freshness signal; confirming the floor is still parked/healthy and re-stating what would
wake it is the value of the run. "Nothing new" is itself the finding. OpenAI view of it:
the silent path still runs monitor_fleet.py and regenerates the ledger — but the report
to the user is NOT suppressed; it is always delivered (see
`templates/fleet-cron-report.md` "Cron-mode deliverable semantics"). Freshness only
upgrades/downgrades the verdict word (DORMANT → PARTIALLY LIVE → LIVE) inside the report;
it never makes the run skippable.
