# Resume / Continue a Large Codebase Rebuild

## When to use
- User says "continue rebuilding our <project>", "finish the <X> program", "keep going on <project>" — i.e. there is already a committed/partial codebase and they want forward progress, not a from-scratch build.
- The repo has several independent components (frontend, backend, pipeline, device-integration, etc.) that can be worked on in parallel.
- Especially relevant for this user's multiple large projects (3D-printing app, trading bot, etc.).

## Steps (foundation-first, then parallelize)
1. **Locate the active repo + git state.** Don't assume the first match is current. Search for the project name; check `git log --oneline`, `git status`, and any rename (e.g. an old name like `3MF_DOOM_BUILDER` renamed to `demiurge-3d`). Confirm which directory is the live one.
2. **Find the roadmap / TODO.** Look for `TODO.md`, `ROADMAP*.md`, `docs/TODO.md`. IMPORTANT: a repo may contain a TODO for a *different sub-product* (e.g. an agent-platform TODO inside a 3D-printing repo) — read it before assuming it lists the next 3D steps. If no in-repo roadmap exists, ask the user which frontier to push (offer concrete, grounded options from the actual file tree).
3. **Establish a baseline health check BEFORE building features.** A "rebuild" can sit on a broken foundation. Verify: does it import? does the dev server build? are deps installed? This also tells you whether later subagent work has a sound base.
4. **Fix the foundation YOURSELF, not via subagent.** Broken/missing venv or uninstalled deps must be repaired first (e.g. `rm -rf .venv && python3 -m venv .venv && .venv/bin/pip install -e .`). Do NOT delegate this: subagents share the filesystem and concurrent `pip install`s into the same venv race and corrupt it. While the install runs in the background, you can kick off independent subagents.
5. **Fan out independent frontiers to parallel leaf subagents** via `delegate_task` with a `tasks` array (max 3 concurrent). Give each a tight, low-exploration brief: exact file paths, the existing patterns to follow, the precise deliverable, and "do NOT touch <other agents' files> / do NOT commit". This is the "full power" parallel mode the user expects.
6. **Verify each frontier with a real run**, not just "it compiles": exercise the CLI/endpoint, confirm output files appear, run the test suite. For web-backed components, do an **E2E server smoke**: launch the real server (`uvicorn server:app --port 8911`) and **probe the exact endpoints the frontend calls** with `curl` (POST the precise JSON the UI sends). This surfaces bugs unit tests miss — e.g. a FastAPI route that `await`s a *sync* function (`return await pipeline.sync_fn()` → `TypeError: 'dict' object can't be awaited`) and **frontend/backend field-contract drift** (UI posts `{request: ...}`, model expects `text`). uvicorn caches imported modules, so **restart the server between fixes** before re-probing.

## Pitfalls
- **Free/slow model subagents TIME OUT.** On the default free model a subagent can burn ~120s per API call and hit the 600s cap mid-task, leaving work half-done. Its file edits are still on disk (uncommitted) — RECOVER by reviewing `git diff` and finishing the work yourself, rather than blindly re-delegating (which may time out again). To reduce risk: give each subagent a low-exploration brief (pre-supply API specifics so it doesn't web-research), and keep its scope small.
- **Don't delegate the dependency foundation.** Repair venv / `pip install` centrally; never let two subagents `pip install` into the same environment concurrently.
- **`python -m <module>` can be a silent no-op.** If a documented entry point (`python -m pipeline.orchestrate "..."`) produces no output and exits 0, the module likely has no `if __name__ == "__main__"` guard — it just imports and returns. Find the real CLI (look for `<pkg>/__main__.py`, a `cli.py`, or a `build()`/`make` command) and drive that instead.
- **Subagent file ownership.** Tell each subagent exactly which files/dirs are theirs and which are owned by sibling agents, so parallel work doesn't clobber. The orchestrator (you) should own cross-cutting integration (server imports, end-to-end wiring).
- **Leave changes uncommitted for review** unless the user explicitly wants a commit; recovering/inspecting `git diff` is far easier on uncommitted work.
- **Frontend/backend field drift → fix in the backend, not the shipped UI.** The frontend may POST a different key than the backend Pydantic model declares (observed: `request` vs `text`). Add `Field(alias="request")` + `model_config = {"populate_by_name": True}` so both keys work. The backend is the contract source of truth — don't edit the already-built frontend to match.
- **Don't `await` sync callables in async routes.** A plain `def` returning a `dict` (`pipeline.understand_text`) written as `return await pipeline.understand_text(...)` raises `TypeError: 'dict' object can't be awaited`. Only `await` coroutines (`async def`). The E2E smoke catches this; unit tests on the pure function won't.
- **Respect command-denials absolutely.** This user blocks commands he hasn't consented to, even read-only probes (`curl` + `python -c` JSON parse was blocked this session). On a block: stop, do NOT re-run or rephrase the same outcome, state what was blocked, and wait. The block is a hard guardrail, not a hint to find a workaround.
- **Subagent-authored tests often don't even COLLECT.** A subagent that builds a feature frequently also drops a `test_*.py` against the API it *imagined*, not the one on disk — referencing fixtures that don't exist (`http_port`, `ws_port`) or attributes the module never exports (`printer_manager` when the real export is `get_printer_manager()`). `pytest` then errors at setup/collection, not at an assertion, so a "build passes" claim from the subagent is NOT proof tests pass. ALWAYS run the suite (`pytest tests/ -q`) after subagent work; if a test errors during collection, `grep` the real module exports and rewrite the test to match the actual API. (Seen this session: the printer test referenced `http_port`/`ws_port` fixtures + a `printer_manager` attribute that didn't exist; rewrote it self-contained and it passed.)
- **FastAPI SPA static-serving trap (bring-up 404s).** When the backend also serves the built frontend, a root mount `app.mount("/static", StaticFiles(directory=BUILD))` SHADOWS the built HTML's bare `/assets/*` links — Starlette routes by longest prefix, so `/assets/index-*.js` is captured by the `/static` mount and 404s. Fix: mount `/assets` EXPLICITLY (`app.mount("/assets", StaticFiles(directory=BUILD/"assets"))`) so bare `/assets/...` resolves, and add an explicit `@app.get("/favicon.svg")` route (the root static mount returns a dir listing, never the file). Point `STATIC_DIR` at the build output (e.g. `frontend/dist`) via an env override. Discovered this session when `/` served 200 but `/assets/*` 404'd until the explicit mount was added.

- **`from __future__ import annotations` breaks dataclass-based config loading.**

- **When LO says a component is missing from the rebuild, check the OLD project's source tree first.** Large project migrations (e.g., `ENI_Swarm` → `ENI_Swarm_NEW`) often port the core code but leave behind whole subsystems — KnowledgeBase directories, script infrastructure (`build_all.py`, `eni_launcher.py`), worker modules (`skill_forge_worker.py` with PatternExtractor + SkillForge classes), and full-featured legacy modules that the new versions stripped down. Don't guess what's missing — list the old project's subdirectories (`KnowledgeBase/`, `scripts/`, `workers/`) and compare against the new one. When you find missing pieces: (a) copy old modules into `lib/kb/legacy/` as parallel modules alongside the new code, (b) fix hardcoded paths (e.g., `~/Desktop/ENI_KB` → `~/.eni/kb`), (c) fix imports in dependent files to use the legacy paths (`from kb.legacy.compression_pipeline import ...`), (d) keep the new test-passing modules intact — never wholesale-replace working code with old versions that have different module-level attributes (different `GLYPH_DB` vs `GLYPH_REGISTRY` names will break the test suite). The old source lives at `~/Desktop/Projects/<OldProject>/` — always check there when LO says "don't see X in the new one."

- **`min()` on empty collections in recycle/eviction paths crashes.** Before `min(collection.values(), key=...)`, guard with `if not collection: raise RuntimeError` or reset to initial state. This hits LRU recycling, glyph allocators, evolution engine population selection, and any code that evicts items when capacity is exhausted but the collection is empty. When a config module uses `from __future__ import annotations` (common in Python 3.12+), all type annotations become strings at runtime. Any code that uses `hasattr(field_type, "__dataclass_fields__")` to detect nested dataclass configs will silently fail because `hasattr("VoiceConfig", "__dataclass_fields__")` is False on a string. Symptom: `cfg.voice.provider` returns `AttributeError: 'dict' object has no attribute 'provider'` because the nested section stayed a plain dict. Fix: add a `_resolve_annotation()` helper that looks up string annotations in the module's globals before checking `hasattr`.

- **`replace_all=true` patch on code with repeated patterns destroys files.** When a function body contains a pattern that also appears in a sibling function (e.g. `if _pool is None:` in both `get_pool` and `close_pool`), `replace_all` inserts the replacement at BOTH locations including at the wrong indentation inside the wrong function, nesting function bodies and producing `SyntaxError`. Fix: never use `replace_all` on code with repeated structural patterns. Use a single targeted match with enough surrounding context to be unique. If the file is already damaged, reconstruct the affected section with `execute_code` (read lines, splice in clean replacement, write back).

- **Settings forms MUST POST to a real API endpoint.** Admin dashboards with settings forms that only show a toast on submit lose all user data on refresh. The form handler must `fetch('/api/settings', {method:'POST', body: JSON.stringify(data)})` and the server must persist to a real file. A toast-only "save" is a data-loss trap.

- **Optional-dependency imports: never set attributes on None.** When wrapping `import psycopg` in try/except with fallback to `psycopg = None`, do NOT write `psycopg.rows = None` in the except block. `NoneType` has no `__dict__` and raises `AttributeError`. Use a `_HAS_PSYCOPG` boolean guard at call sites instead.

- **When an API token returns 404 across every endpoint, STOP retrying.** After 3 distinct endpoints all return the same fatal error from the same credential, inform the user and ask them to verify on their side. Do not cycle through HTTP libraries — the API is rejecting the credential.

- **Inject topnav as the FIRST element after `<body>`, not the last.** When a unified server injects a shared navigation bar into served HTML pages, the toast notification system must appear ABOVE the nav. Use `z-index: 2147483647 !important` on both the toast container and individual toast elements, and set the nav's z-index lower (e.g. 10000). Add `position: relative !important` to individual toasts so they establish their own stacking context.
